# Mobv VOC 분류 정책

| 항목 | 내용 |
| --- | --- |
| 버전 | v1.0 |
| 기준일 | 2026-10-16 |
| 목적 | 가상 Mobv VOC에 일관된 정답 라벨을 부여하고 AI·규칙·사람의 판단 기준을 통일한다. |
| 적용 범위 | 개발 세트, 평가 세트, AI 출력 검증, 운영자 검토 화면 |

## 1. 분류 단위

각 VOC는 다음 네 축으로 분류한다.

1. `category`: 어떤 종류의 문의인가?
2. `product_area`: Mobv의 어느 기능에서 발생했는가?
3. `priority`: 얼마나 빨리 확인해야 하는가?
4. `owner`: 어느 담당 영역이 먼저 확인해야 하는가?

대표 유형은 하나만 지정한다. 하나의 문장에 여러 문제가 있으면 가장 영향도가 높은 문제를 대표 유형으로 선택하고 나머지는 `secondary_category`와 `MULTI_ISSUE` 플래그로 기록한다.

---

## 2. VOC 유형

| 코드 | 정의 | 포함 | 제외·경계 |
| --- | --- | --- | --- |
| `BUG` | 이미 제공되는 기능이 의도대로 작동하지 않음 | 버튼 미작동, 저장 실패, 잘못된 추천·집계·확정, 앱 종료 | 기능 위치를 모르거나 문구가 어려운 문제는 `USABILITY` |
| `USABILITY` | 기능은 작동하지만 발견·이해·조작이 어려움 | 상태 피드백 부족, 원의 의미 불명확, 버튼 위치 혼란 | 기능 자체가 실패하면 `BUG` |
| `REQUEST` | 현재 없는 기능이나 옵션을 요구함 | 공유 링크, 다크 모드, 세부 필터 | 기존 기능 사용법 질문은 `INFORMATION` |
| `ACCOUNT` | 계정 접근과 인증 절차에 관한 문의 | 인증 메일, 로그인 방법, 계정 삭제 요청 | 로그인 기능 자체의 재현 가능한 오류는 `BUG`를 대표 유형으로 사용 가능 |
| `POLICY` | 개인정보, 권한, 보안, 데이터 보관, 운영 기준 | 다른 약속 데이터 노출, 데이터 삭제·보관 문의 | 단순 기능 설명은 `INFORMATION` |
| `INFORMATION` | 사용법이나 처리 기준을 묻는 문의 | 초대 코드 유효기간, 투표 방식, 방장 권한 | 기능 추가 요청은 `REQUEST` |
| `ETC` | 정보가 부족하거나 허용 유형으로 판단하기 어려움 | “안돼요”, 맥락 없는 감정 표현 | 추가 맥락으로 다른 유형을 판단할 수 있으면 해당 유형 사용 |

### 유형 결정 순서

1. 개인정보·권한·보안 문제이면 `POLICY`를 우선 검토한다.
2. 제공 중인 기능이 실제로 실패하면 `BUG`를 검토한다.
3. 기능은 동작하지만 이해나 조작이 어렵다면 `USABILITY`로 분류한다.
4. 존재하지 않는 기능을 요구하면 `REQUEST`로 분류한다.
5. 계정 처리나 인증 절차 문의는 `ACCOUNT`로 분류한다.
6. 사용법이나 기준 질문은 `INFORMATION`으로 분류한다.
7. 판단 근거가 부족하면 `ETC`와 `AMBIGUOUS`를 사용한다.

### 경계 사례

| VOC | 대표 유형 | 이유 |
| --- | --- | --- |
| “로그인 버튼을 누르면 앱이 꺼져요.” | `BUG` | 인증 문의가 아니라 기능 실패가 핵심 |
| “로그인 방법을 모르겠어요.” | `ACCOUNT` | 계정 접근 절차 문의 |
| “원이 저장됐는지 표시가 없어서 모르겠어요.” | `USABILITY` | 저장 실패가 확인되지 않았고 상태 피드백이 문제 |
| “원을 저장했는데 다시 들어오면 사라져요.” | `BUG` | 저장 또는 조회 실패가 확인됨 |
| “약속 결과를 카카오톡으로 공유하고 싶어요.” | `REQUEST` | 현재 없는 기능 요청 |
| “초대 코드는 언제까지 쓸 수 있나요?” | `INFORMATION` | 운영 기준과 사용법 문의 |

## 3. 제품 영역

| 코드 | 포함 기능 | 대표 키워드 |
| --- | --- | --- |
| `AUTH` | 로그인, 회원가입, 인증, 닉네임, 프로필 색상, 계정 삭제 | 로그인, 가입, 인증, 계정, 닉네임 |
| `APPOINTMENT` | 약속 생성, 초대 코드, 참여, 나가기, 삭제, 정원 | 약속, 방, 초대, 참여, 나가기 |
| `DATE_COORDINATION` | 후보 날짜, 시간대, 일정 투표, 방장 날짜 확정 | 날짜, 시간, 일정, 달력, 방장 |
| `MAP_LOCATION` | 카카오맵, 현재 위치, 위치 권한, 원 그리기, 반경, 참여자 원 | 지도, 위치, 원, 반경, GPS |
| `RECOMMENDATION` | 교집합, 카테고리, 추천 장소, 카카오 장소 상세 | 추천, 교집합, 카페, 맛집, 장소 |
| `VOTING` | 장소 투표, 투표 현황, 동점, 최종 확정 | 투표, 득표, 동점, 확정 |
| `HISTORY` | 확정 기록, 히트맵, 방문 메모 | 기록, 히트맵, 메모, 지난 약속 |
| `COMMON` | 앱 전반, 성능, 네트워크, 접근성, 범위를 특정할 수 없는 문제 | 느림, 글자, 화면 전체, 네트워크 |

여러 영역이 포함되면 사용자 피해가 가장 큰 영역을 `product_area`로 선택하고 나머지를 `secondary_product_area`에 기록한다.

## 4. 우선순위

| 등급 | 판단 기준 | Mobv 사례 | SLA |
| --- | --- | --- | --- |
| `P0` | 실제 또는 강하게 의심되는 개인정보 노출·권한 우회, 다수 사용자의 핵심 기능 전면 중단 | 다른 약속의 위치·메모가 보임, 모든 사용자가 로그인 불가 | 즉시 확인 |
| `P1` | 핵심 흐름 차단, 데이터 손실, 잘못된 약속 확정, 중요한 권한 오류 | 전원 투표 전 장소 확정, 날짜 투표 전체 유실 | 당일 |
| `P2` | 일부 기능 오류지만 우회 가능, 특정 환경에 한정된 장애 | 현재 위치가 부정확하지만 지도 수동 이동 가능 | 3영업일 이내 |
| `P3` | 단순 문의, 경미한 사용성 문제, 기능 제안 | 다크 모드 요청, 초대 코드 사용법 질문 | 5영업일 이내 |

### 우선순위 결정 질문

1. 개인정보나 다른 사용자의 데이터가 노출되는가?
2. 권한이 없는 사용자가 조회·수정·확정할 수 있는가?
3. 로그인부터 약속 확정까지의 핵심 흐름이 완전히 막히는가?
4. 저장된 데이터가 사라지거나 잘못된 결과로 확정되는가?
5. 우회 방법이 있는가?
6. 일부 환경에만 발생하는가?
7. 단순한 안내 또는 기능 제안인가?

### 규칙 기반 최소 우선순위

| 조건 | 최소 우선순위 | 추가 처리 |
| --- | --- | --- |
| 개인정보 노출 또는 다른 약속 데이터 접근 | `P0` | `PRIVACY_SECURITY`, 반드시 검토 |
| 권한 없는 날짜·장소 확정 | `P1` | `PRIVACY_SECURITY`, 반드시 검토 |
| 로그인·약속 생성·추천·투표 전체 차단 | `P1` | `HIGH_PRIORITY`, 반드시 검토 |
| 데이터 삭제·유실·중복 확정 | `P1` | `HIGH_PRIORITY`, 반드시 검토 |
| 위치 오차이나 수동 조작 가능 | `P2` | 필요 시 플랫폼 정보 확인 |
| 기능 요청·사용법 문의 | `P3` | 법적·접근성 요구는 사람 검토 |

## 5. 담당 영역

| 코드 | 책임 범위 | 대표 사례 |
| --- | --- | --- |
| `DEVELOPMENT` | 코드, 데이터, API, 성능, 장애 재현 | 저장 실패, 앱 종료, 투표 중복 |
| `DESIGN_UX` | 정보 구조, 문구, 발견성, 조작, 접근성 | 원의 의미 불명확, 버튼 위치 혼란 |
| `PRODUCT` | 기능 범위, 우선순위, 제품 정책 | 공유 기능, 필터, 반복 모임 기능 요청 |
| `OPERATIONS` | 이용 안내, 사용자 확인, 운영 처리 | 초대 코드 안내, 계정 상태 확인 |
| `POLICY_SECURITY` | 개인정보, 권한, 데이터 보관, 보안 정책 | 다른 약속 데이터 노출, 삭제 요청 기준 |
| `NEEDS_TRIAGE` | 정보 부족, 복합 문제, 담당 확정 불가 | “안돼요”, 재현 정보가 전혀 없음 |

대표 담당 영역은 최초 확인 주체다. 협업이 필요한 경우 `secondary_owner`를 기록한다.

## 6. 검토 플래그

| 플래그 | 발생 조건 |
| --- | --- |
| `HIGH_PRIORITY` | P0 또는 P1 |
| `PRIVACY_SECURITY` | 개인정보·위치정보·권한·보안 관련 내용 |
| `MULTI_ISSUE` | 서로 다른 두 개 이상의 문제가 포함됨 |
| `AMBIGUOUS` | 문장이 짧거나 필요한 맥락이 없음 |
| `INVALID_OUTPUT` | AI 출력의 필수값 누락 또는 허용값 위반 |
| `RULE_OVERRIDE` | 규칙이 AI 우선순위·담당 영역을 수정함 |
| `LOW_CONFIDENCE` | AI가 낮은 확신도를 표시함 |
| `PERSONAL_DATA` | 이메일·전화번호 등 개인정보 형식 감지 |
| `PROMPT_INJECTION` | 사용자 문장에 시스템 지시 변경을 요구하는 표현 포함 |

### `needs_review` 결정

다음 중 하나라도 해당하면 `needs_review=true`로 설정한다.

- 우선순위가 P0 또는 P1
- `PRIVACY_SECURITY`, `MULTI_ISSUE`, `AMBIGUOUS`, `INVALID_OUTPUT`, `RULE_OVERRIDE`, `LOW_CONFIDENCE`, `PERSONAL_DATA`, `PROMPT_INJECTION` 중 하나 이상 존재
- 담당 영역이 `NEEDS_TRIAGE`
- 유형이 `ETC`

## 7. AI·규칙·사람의 역할

### AI

- 한 줄 요약
- 대표 유형과 제품 영역 초안
- 우선순위와 담당 영역 초안
- 판단 이유와 확신도 단계 생성

### 규칙

- 허용값과 필수값 검증
- 개인정보 패턴 마스킹
- 개인정보·권한·핵심 장애 최소 우선순위 적용
- 검토 플래그와 `needs_review` 결정
- 실패 결과 재시도 및 오류 목록 기록

### 사람

- P0·P1과 모든 검토 대상 최종 확인
- AI 최초값과 규칙 보정 결과 승인 또는 수정
- 수정 이유 기록
- 실제 처리 우선순위와 개선과제 채택 결정

## 8. 정답 라벨 작성 절차

1. VOC 원문만 읽고 대표 문제를 한 문장으로 적는다.
2. `category`와 `product_area`를 각각 선택한다.
3. 사용자 피해와 우회 가능성을 기준으로 `priority`를 선택한다.
4. 최초 확인 주체를 `owner`로 선택한다.
5. 검토 플래그를 지정한다.
6. 한 문장으로 판단 이유를 기록한다.
7. 경계 사례는 별도 목록에 남기고 정책을 보완한다.

정답 라벨은 AI 출력을 보기 전에 작성한다. 평가 세트의 정답은 최종 평가 전까지 분류 코어와 프롬프트 수정에 사용하지 않는다.

---

## 9. 정책 변경 원칙

- 분류 코드가 변경되면 개발·평가 데이터와 출력 검증 규칙을 함께 갱신한다.
- 평가 세트 결과가 좋지 않다는 이유만으로 정답 기준을 사후 변경하지 않는다.
- 기준이 실제로 모호했다면 변경 이유와 이전·이후 버전을 기록한다.
- 정책 버전은 모든 실행 로그에 포함한다.

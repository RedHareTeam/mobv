# Day 2 가상 VOC 데이터

개발·평가 세트의 50건과 별도 수작업 기준선 입력은 Mobv 출시 후 운영을 가정해 만든 **가상 사례**다. 실제 고객 문의나 운영 실적이 아니다. `app_version=unknown`은 특정 출시 버전을 가정하지 않기 위한 값이다. 이메일은 `example.com`, 전화번호는 `010-0000-0000`처럼 테스트용 형식만 썼다. 아래 분포와 검증 수치는 개발·평가 세트 50건에 관한 것이다.

| 세트 | 입력 | 정답 | 용도 |
| --- | ---: | ---: | --- |
| 개발 | `development_voc.csv` 30건 | `development_gold.csv` 30건 | 프롬프트·규칙 설계와 오류 수정 |
| 평가 | `evaluation_voc.csv` 20건 | `evaluation_gold.csv` 20건 | 구현이 끝난 뒤 최종 성능 측정 |

`manual_baseline_voc.csv`는 Day 4에 추가한 별도의 가상 입력 30건이다. 기존 개발 결과를 이미 본 사람이 수작업 처리시간을 측정할 때 쓰며, 정답 파일은 만들지 않았다. 평가 정답과도 연결하지 않는다.

첫 수작업 시도가 3건에서 중단되어 저장된 기준선은 없다. 처음 본 문장을 다시 측정하지 않도록 `manual_baseline_v2_voc.csv` 30건을 새로 만들고 측정 도구의 기본 입력으로 지정했다. 이 파일에도 정답은 없고 평가 정답과 연결하지 않는다. 이전 파일은 연습용으로만 남긴다.

정답에는 [분류 정책](../docs/classification-policy.md) v1.0의 유형·제품 영역·우선순위·담당 영역·SLA·검토 플래그와 한 문장 이유를 기록했다. 평가 입력 파일에는 정답 열이 없으며, 평가 정답과 아래 분포표는 분류 프롬프트·규칙 튜닝에 사용하지 않는다. 평가 시에는 입력 CSV만 분류기에 전달한 뒤 결과를 정답과 비교한다.

## 구성과 경계 사례

- P0·P1 19건, 복합 문제 3건, 짧고 모호한 문장 3건, 가상 개인정보 형식 3건, 프롬프트 인젝션 형태 2건을 포함했다.
- 같은 문제를 다르게 말한 개발 세트 사례: 초대 코드 참여 실패 `DEV-002`/`DEV-019`, 저장한 원 유실 `DEV-006`/`DEV-025`, 투표 중복 집계 `DEV-011`/`DEV-029`.
- 평가 세트에도 비슷한 문제를 새 문장으로 넣어 표현 차이를 확인할 수 있게 했다. 정확도 계산 때는 20건 모두 개별 VOC로 센다.
- 긴급·예외 사례를 의도적으로 많이 배치했다. 이 분포를 실제 서비스의 VOC 발생 비율로 해석하면 안 된다.
- `gold_review_flags`가 비어 있으면 자동 검토 플래그가 없다는 뜻이다. `gold_needs_review`는 `true` 또는 `false`다.

## 검증

프로젝트 루트에서 `python scripts/validate_day2_data.py`를 실행한다. CSV 파싱, 행 수, ID의 순서·유일성, 입력·정답 분리, 허용값, SLA, 우선순위·검토 플래그 일치, 예외 사례 수를 확인하고 분포를 출력한다. 문장 해석의 적절성은 [분류 정책](../docs/classification-policy.md)의 경계 사례에 따라 사람이 별도로 검토한다.
